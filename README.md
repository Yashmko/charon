# Charon

**Deterministic, evidence-driven HTTP authorization analysis.**

Charon ingests captured HTTP traffic, replays requests under alternate identities,
compares responses, and creates traceable findings for authorization weaknesses
such as BOLA/IDOR, BFLA, and BOPLA. Its deterministic core is designed so findings
are derived from recorded artifacts rather than generated by an LLM. Advisory
LLM enrichment is optional by design and must never create or suppress findings.

## Pipeline

```text
capture → replay → compare → detect → report
```

| Module | Capability |
| --- | --- |
| `model` | Immutable, content-addressed artifacts with provenance tags |
| `capture` | HAR and raw-dictionary ingestion, normalization, configurable sensitive-header handling |
| `replay` | HTTP replay using bearer tokens, cookies, API keys, or custom headers |
| `compare` | Deterministic response comparison and volatile-field suppression |
| `detect` | BOLA, BFLA, BOPLA, missing-authorization signals, and matrix analysis |
| `report` | Deterministic JSON and Markdown reports with evidence traceability |
| `pipeline` / `cli` | Stage orchestration and `charon analyze` command |

## Quick start

Install the replay extra:

```bash
python -m pip install "charon[replay]"
```

Analyze a HAR capture with a credential file:

```bash
charon analyze capture.har \
  --credentials creds.json \
  --format both \
  --output authorization-report.txt
```

Credential file example:

```json
[
  {
    "label": "test-user-b",
    "bearer_token": "REPLACE_WITH_A_TEST_TOKEN"
  }
]
```

Supported credential inputs are bearer tokens, cookies, API keys with a
configurable header name, and extra headers. Prefer a protected credentials
file over inline command-line secrets because shell history and process listings
can expose inline values.

Formats: `json`, `markdown`, and `both`. The CLI also supports
`charon version`; run `charon analyze --help` for options.

## Validation and trust boundaries

A finding is an evidence-backed candidate for investigation, not a guarantee of
a vulnerability. Detection quality must be measured against labeled test cases;
unit-test success alone does not establish precision or recall. See
[`docs/validation-plan.md`](docs/validation-plan.md) for a local validation
approach and metrics, and
[`docs/security-and-data-handling.md`](docs/security-and-data-handling.md)
for scope, credentials, capture, and report safety guidance.

**Important data note:** the default capture policy redacts configured sensitive
header values, but does not currently scrub request/response bodies, URL query
values, or every possible custom secret-bearing header. Review and sanitize
captures before sharing or committing them.

| Detection category | Mapping |

| BOLA / IDOR (cross-account object access) | API1: Broken Object Level Authorization |
| BOPLA (sensitive property exposure) | API3: Broken Object Property Level Authorization |
| BFLA (privileged function access) | API5: Broken Function Level Authorization |

## Ethics

Use Charon only on systems for which you have explicit authorization and a
defined test scope. Replaying captured requests can trigger application-side
effects. Prefer dedicated test identities and synthetic data, and stop when
scope or expected impact is unclear.
